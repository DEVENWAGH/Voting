# System Architecture — Updated 12-Module Specification (VotingV3)

> **Contract Standard**: `VotingV3.sol` ONLY (UUPS Upgradeable Proxy pattern)  
> **External API Policy**: Removed external third-party API dependencies (No AWS Rekognition SDK, No ImageKit SDK, No Pinata IPFS API, No Cloudflare Workers/AWS Wavelength external services). Built strictly using native Next.js API routes, Node.js `crypto`, MongoDB/Mongoose, and Ethers.js internal capabilities.  
> **Module Names**: Exactly matches all 12 original module names.

---

## 12-Module System Specification Table

| Module Name | Problem Statement / Requirement | Technical Solution / Architecture | Tech Stack | Key API Endpoints / Methods |
|---|---|---|---|---|
| **Organization Onboarding & Authentication** | Organizations need a secure way to register and authenticate administrators to manage elections, candidates, and voters without unauthorized access. | Provides an onboarding workflow. Administrators register using organization profiles and verified email addresses, with secure session-based authentication managing admin dashboard routes. | Next.js (API Routes), NextAuth.js (v5), MongoDB/Mongoose, Nodemailer, bcryptjs | `POST /api/org-auth/signup`<br>`POST /api/org-auth/verify-email`<br>`GET/POST /api/auth/*` (NextAuth.js routes) |
| **Multi-Sign Governance & Smart Contract Upgradeability** | Centralized smart contracts are vulnerable to single points of failure, while immutable contracts cannot be patched to fix bugs or introduce improvements. | Implements a 2-of-3 Guardian multi-signature approval mechanism for contract upgrades. Upgrades are proposed on-chain, approved by guardians, and executed using the OpenZeppelin UUPS upgradeable proxy pattern strictly targeting `VotingV3.sol`. | Solidity (`VotingV3`), Hardhat, OpenZeppelin UUPS Upgradeable Contracts, Ethers.js | `POST /api/admin/elections/approveOn-chain`<br>On-chain methods:<br>`proposeUpgrade()`, `approveUpgrade()`, `executeUpgrade()` |
| **Gasless Transaction Relay (Gas Station)** | Requiring voters to set up crypto wallets (e.g., MetaMask) and acquire ETH creates a high-friction barrier. | Integrates a gas station relay where the administrator pays transaction fees. The relay manages transaction queues and nonces before submitting transactions on-chain. | Ethers.js (JsonRpcProvider, NonceManager), MongoDB/Mongoose (RelayTransaction Model), Hardhat | `GET /api/relay/status`<br>`GET /api/relay/transactions`<br>`POST /api/relay/vote` |
| **Election Lifecycle & State Machine** | Election phases (Registration, Voting, Completed) must be strictly enforced to prevent invalid actions. | Implements an on-chain state machine inside `VotingV3.sol`. Candidate registration is allowed only during Registration, voting only during Voting, and result processing only during Completed. | Solidity Smart Contract (`VotingV3`), Ethers.js, Next.js API Routes, MongoDB | `GET/POST /api/org/[slug]/elections`<br>`POST /api/org/[slug]/elections/[id]/phase`<br>`GET /api/elections/public` |
| **Candidate Directory & Rich Profiling** | Candidate details, images, and manifestos are too large and expensive to store directly on-chain. | Stores candidate profile images, manifestos, and rich metadata internally in MongoDB database models and server routes, registering candidate references on-chain within `VotingV3.sol` without requiring external image hosting or IPFS APIs. | Next.js, Ethers.js, MongoDB/Mongoose (`Candidate` Model) | `POST /api/org/[slug]/elections/[id]/candidates`<br>`GET/POST/PATCH /api/candidates` |
| **Bulk Voter Roster & Preflight Verification** | Manually registering thousands of voters is slow, and duplicate or unauthorized voter addresses must be detected. | Supports CSV bulk upload, duplicate detection, generation of unique deterministic nullifier hashes (`keccak256`), and pre-registration through the gas station relay into `VotingV3.sol`. | Next.js, csv-parser, MongoDB/Mongoose, Ethers.js | `POST /api/voters/upload-csv`<br>`POST /api/voters/bulk-register`<br>`GET /api/voters/list` |
| **2FA-Verified Gasless Voting Flow (Email OTP + Face Recognition)** | Votes must be securely authenticated, verified, and recorded while maintaining ballot secrecy. | Implements Two-Factor Authentication using email OTP (Nodemailer) and face verification before issuing a biometric verification JWT. The server validates the OTP and biometric JWT before relaying the private vote on-chain to `VotingV3.sol` using `castVotePrivate()`. | Next.js, Nodemailer, JWT, Ethers.js, Solidity Contract (`VotingV3`) | `POST /api/auth/send-otp`<br>`POST /api/auth/verify-otp`<br>`POST /api/biometric/verify`<br>`POST /api/relay/vote` |
| **Cloud-Based "Zero-Knowledge" Biometric Authentication** | Prevents voter impersonation and double voting while handling facial verification. | Captures a live face feed client-side (HTML5 Canvas/Camera API) and performs face detection and liveness validation via internal server-side processing and local facial landmark verification, generating a short-lived (60-second) JWT upon success. Does not rely on external cloud biometric APIs. | Next.js (HTML5 Canvas/Camera API), Node.js Internal Crypto/Landmarks, MongoDB, JWT | `POST /api/biometric/register`<br>`POST /api/biometric/verify` |
| **Serverless Real-Time Analytics Dashboard** | Blockchain networks are optimized for integrity, not real-time analytics and charting. | Uses serverless backend routes and MongoDB Atlas aggregation pipelines to monitor `VotingV3` election events, store them in MongoDB, and dynamically generate turnout statistics and charts. | Next.js, MongoDB Atlas (Aggregation Pipeline), Ethers.js, TanStack Query, SVG/Recharts | `GET /api/analytics/[electionId]`<br>`GET /api/elections/[id]/results`<br>`GET /api/elections/[id]/activity` |
| **Edge Computing for Low Latency (Cloud-Edge Hybrid)** | Heavy voting traffic can overload blockchain nodes, causing congestion and unnecessary gas costs. | Performs lightweight preflight validation at the edge/middleware level using Next.js Middleware and MongoDB/in-memory caching before queuing and relaying transactions to `VotingV3.sol`. Avoids external edge worker services. | Next.js API Middleware, MongoDB Cache, Ethers.js | `POST /api/preflight` |
| **Voter Cryptographic Key Storage Utility (AES-256 + SHA-256)** | Voter cryptographic keys must be securely generated, stored, and restored without exposing plaintext private keys. | Uses PBKDF2 (100,000 iterations) with SHA-256 to derive encryption keys and AES-256-GCM to securely encrypt Ethereum private keys / nullifiers for client-side wallet storage. | Web Crypto API (SubtleCrypto), Ethers.js (Wallet) | Helper library functions (executed client-side/utility-side) |
| **Public Audit Trails & Verification** | Voters and auditors must be able to verify that their votes were correctly counted and recorded on-chain without revealing who they voted for. | Sends a transaction receipt containing a unique transaction hash (`txHash`) to the voter via email. A public verification interface allows anyone to verify that the transaction is confirmed on-chain in `VotingV3.sol` (`VoteCastPrivate` events) and matches election parameters, ensuring transparency while preserving voter anonymity. | Next.js, Ethers.js, Hardhat (Solidity `VotingV3` Events), crypto (SHA-256) | `GET /api/audit/verify` |
